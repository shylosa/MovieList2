# R14-B. Реальна вибірка назв файлів, офлайн

Перевірка діагностики [R14-A](RECOGNITION_REAL_FILENAMES_BASELINE.md) на реальних назвах файлів із приватного каталогу власника. Базовий коміт `06010f91d02ade00ab457d30a13d99b7c9df35c6`. Дослідницький етап: production-код, SQLite, медіафайли, live API не змінювалися й не запускалися. Механізм — єдиний, [r14_filename_diagnostic_test.go](../../internal/tmdb/r14_filename_diagnostic_test.go).

## Джерело й склад вибірки

- Джерело: один приватний каталог медіатеки, за явним дозволом власника. Читалися лише імена файлів і структура папок, без вмісту. Інші каталоги не обходилися.
- Вибірка: **50 рядків** = 36 файлів верхнього рівня + 12 із вкладених папок + 2 контрольні проби (`1917.mkv`, `12.mkv`).
- Покриття: назви без року та з роком; числові токени в назві; короткі назви; серіали (`S01E01`, `s01e01`, `S01.E01`, `Season 1`, `(s01)`); кирилиця, латиниця, змішані абетки; вкладені папки; технічні маркери. Окремим рядком — Guarding Stars (`Охрана звёзд`, оракул `movie:1551025` із відомого ручного підтвердження, див. [аудит](AI_TMDB_FALLBACK_AUDIT.md#5-guarding-stars)).
- Оракул (CleanTitle/рік/тип/TMDB ID) заповнений до запуску з незалежних міркувань; невідомі поля порожні. Приватні артефакти (`input.tsv`, детальний `report.json`) зберігаються поза репозиторієм; у цьому звіті реальні назви файлів і шляхи замасковані.

## Запуск

З кореня репозиторію, зі своїм приватним списком і `-r14-root` кореня медіаджерела:

```powershell
go test ./internal/tmdb -run '^TestR14FilenameReport$' -count=1 -args -r14-input $list -r14-output $report -r14-root $root
```

Транспорт фікстури відповідає в пам’яті лише на `/3/search/movie`, `/3/search/tv` і `/3/find/{imdb}`; будь-який інший запит (details, постери, чужий ключ) завершується помилкою, тому тест PASS означає повну відсутність live-звернень. `api_key` у звіт не потрапляє. App, SQLite, AI не ініціалізуються.

## Статистика пошукових запитів

- Typed search (`/3/search/movie|tv`): **286 загалом**, у середньому 5.72 на файл, максимум 17, розподіл `{0:2, 2:2, 3:16, 4:4, 5:10, 6:1, 9:9, 11:1, 13:3, 14:1, 17:1}`.
- IMDb `/find`: 0 (у вибірці немає tt-ID).
- Нуль typed search: **2/50**, обидва — контрольні проби (див. нижче); серед 48 реальних файлів нульових немає.
- Порядок: латиниця → `en-US`; кирилиця → `uk-UA` → `ru-RU` → трансліт у `en-US`; для movie параметр `year`, для TV `first_air_date_year`; кожна назва спочатку з роком, потім без — як за дизайном.
- Parent fallback спрацював у 7 сценаріях (зокрема батьківська папка дала рік 2026 для серіалу та 2024 для фільму); корінь джерела коректно відсікався.
- Підозрілі fallback-запити: у **14/50** сценаріях fallback-кандидати містять технічні маркери (часткові дужки, однобуквені кодеки, розміри на кшталт `1 37 gb`, платформні префікси, `DD5 1`, назва студії дубляжу, маркер реліз-групи, `S01E01 WEB…` тощо); **32** трансліт-запити з кириличних назв; **2** фонетичні запити латиниця→кирилиця зі змішаними абетками у query.

## Підтверджені дефекти

1. **Чисто числова назва з’їдається як рік.** `1917.mkv` → `CleanTitle=""`, `Year=1917`, **0 typed search**. Причина: [parser.go](../../internal/tmdb/parser.go#L63) бере перше число з `reYear` у діапазоні `(1900, now+1]` як рік, не перевіряючи, що це вся назва. Клас: будь-яка назва-число 1901–2027. Підтверджено на синтетиці R14-A і на цій вибірці.
2. **Кандидат коротший за 3 руни відсікається.** `12.mkv` → `CleanTitle="12"`, `Year=0`, але **0 typed search**: правило `len([]rune(c)) > 2` у `generateTitleCandidates` ([search.go](../../internal/tmdb/search.go)). Клас: назви з 1–2 символів. Parse за оракулом OK, але пошук мовчазно не стартує.
3. **Неконсистентна нормалізація року в title.** Назва з токеном `2O16` (O замість 0) і однобуквеним маркером якості дала `Year=2016`, але `CleanTitle` лишився з `2O16` і маркером; fallback йшов із повним технічним хвостом. Year-детект бачить нормалізований рядок (`normalizeYearLikeTokens`, [parser.go](../../internal/tmdb/parser.go#L52)), а очищення назви — ні.

## Підозрілі випадки

- Fallback-кандидати з технічними маркерами (14 сценаріїв) і фонетичний трансліт маркерів у кирилицю — марні HTTP-спроби; офлайн неясно, чи шкодять вони live-scoring.
- Найдовші каскади (11–17 запитів) — усі сценарії з «брудними» хвостами назв.
- Для серіалу з роком лише в дужках батьківської папки (умовно «Назва (S09) (2024)…») `Parsed.Year=0` і батьківський запит без року не потрапив у план, тоді як для іншого серіалу батьківський 2026 підвантажився — можлива неконсистентність parent fallback для папок із маркером сезону.

## Числові та короткі назви

- Числові токени **всередині** назви (умовно «Назва 2», «Назва 101», кириличні аналоги) — усі такі сценарії PARSE_OK, пошук іде нормально.
- Проблема лише для **чисто числової** назви (`1917.mkv` — 0 запитів) і **1–2-символьної** (`12.mkv` — 0 запитів). Це підтверджені дефекти парсера/кандидатів, а не правил пошуку.

## Що неможливо перевірити офлайн

Фактичну TMDB identity, роботу scoring/ранжування, чи «брудні» fallback-запити породжують хибні збоги в live, alias-запити та details — фікстура завжди порожня, тому `identity_status=NEEDS_LIVE_VERIFICATION` для всіх 50. Частоту дефектів у повній медіатеці (вибірка 50 файлів) — лише розширеним офлайн-прогоном або live-сканом.

## Бюджет наступного live TMDB-експерименту

- Вибірка: ті самі 50 рядків або підвибірка 20 (2 числові/короткі проби + 6 «брудних» + Guarding Stars + 11 звичайних).
- Офлайн-каскад у гіршому разі дає до 17 typed search на файл → верхня межа ~286 search + ~50–100 details/aliases для 50 файлів; із раннім виходом реально ~150–250 запитів. За лімітом TMDB це ~1–2 хв чистого часу, до 5 хв із паузами. Правило зупинки: стоп за першим прийнятним збігом на файл; усі URL — у приватний лог поза Git.

## Рекомендації наступних атомарних змін

1. Чисто числова назва ≠ рік: якщо весь basename — число в (1900, now+1], трактувати його як назву з `Year=0` (або обидва варіанти кандидатів). Локальний diff у `ParseFilename`.
2. Для чисто числових/1–2-символьних назв обійти правило `> 2` рун у кандидатах (дозволити ≥1 цифру, коли кандидат — усе, що лишилося).
3. Чистити `CleanTitle` від тієї ж нормалізованої year-послідовності, що йде в `Year`.
4. Окремим погодженим live-прогоном перевірити, чи шкодять маркерні fallback-запити та фонетичний трансліт; лише після evidence — фільтрацію маркерів у кандидатах.

## Перевірки

- `go test ./internal/tmdb -run 'TestR14OfflineDiagnostic|TestR14BadInput|TestR14Cancellation'` — ok; `TestR14FilenameReport` на вибірці — PASS.
- Live API відсутні: будь-який запит поза фікстурою падає тест; poster/details відхилено unit-тестом; production SQLite не змінена (App/SQLite не ініціалізуються); медіафайли не читалися.
- `git status` чистий до й після запуску діагностики; змін у production-коді немає; commit/push не виконано.

## Головне питання

На реальній вибірці 50 назв підтверджено три дефекти, усі в парсері/кандидатах, а не в правилах пошуку: (1) чисто числова назва в діапазоні 1901–2027 з’їдається як рік і лишається без жодного запиту (`1917.mkv`); (2) кандидат до 2 рун відсікається і теж лишається без запитів (`12.mkv`); (3) ненормалізований year-токен (`2O16`) лишається в `CleanTitle` і роздуває fallback. Першими виправляти (1) і (2) — це єдині випадки з повною відсутністю пошуку, виправлення локальне; потім (3). «Брудні» fallback-запити та фонетичний трансліт маркераів — потенційна проблема ефективності (14/50, до 17 запитів), але їхній вплив на точність треба спочатку довести live-прогоном із бюджетом ~150–250 запитів. Перебудова архітектури не потрібна.

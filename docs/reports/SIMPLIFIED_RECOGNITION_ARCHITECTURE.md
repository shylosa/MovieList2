# Спрощення розпізнавання MovieList 2

## 1. Executive Summary

Рекомендація для експерименту: **B, один координатор автоматичного розпізнавання в наявному пакеті `main`**. Найдорожча для розуміння частина сьогодні: після однієї відповіді TMDB розробникові доводиться простежувати, хто її отримав, яку саме перевірку пропущено через кеш, з яким файлом зіставлено рядок AI і чи відбувся commit. Кількість пакетів мало пояснює цю складність.

Дві конкретні зміни дозволяють перевірити ідею окремо. Прибрати TMDB Search L1, який переносить позитивне або негативне рішення між файлами. Вивести AI L2 з автоматичного шляху, де він вводить другу політику підтвердження. Повне припинення запису L2 залежить від відтворення ручного пошуку за попередньою AI-назвою. Коректність B, ціна повторів і користь наступної моделі залишаються предметом експерименту.

## 4. Проблеми розподіленої логіки

1. **Завершення пошуку.** `searchAndFetch` обирає кандидата, отримує details і кешує його. `trySearch` лише потім перевіряє рік. Вхідний L1 hit у `FetchFromParsed` повертає результат до цієї перевірки. Негатив на базовій спробі так само завершує весь файл до аналізу іншої папки. Це встановлює можливий шлях помилки за кодом. Частота в бібліотеці невідома.
2. **Перехід до AI.** Мережеві збої окремих endpoint можуть перетворитися на порожній best, помилки наступних спроб логуються й губляться. Воркер виставляє `needsGemini` за відсутністю позитивного ID. AI не може виправити недоступний TMDB. Потрібно донести характер завершення через усі рівні до координатора.
3. **Перехід до моделі.** `requestWithRetry` завершується на декодованому JSON. Успіх для клієнта може означати empty для App. Missing ID сьогодні запускає новий singleton cascade, тоді як зіставлений empty проходить rescue й може завершитись unresolved. У Guarding Stars попередній аудит встановив один inference і ручний вибір movie:1551025. Автоматичний ефект іншої моделі, L1 або заміни ё/е не встановлено. [Історичний аудит](AI_TMDB_FALLBACK_AUDIT.md)
4. **Прийняття і commit.** До `SaveMoviesBatch` App вже збільшує tmdbAccepted або додає filename до recognizedFiles та пише L2. Окремо SQL захищає існуючий запис. Це три різні події: перевірена гіпотеза, спроба запису, підтверджений рядок каталогу. Метрики та події про збереження мають походити з останньої. Помилка L2 invalidation у Confirm може повернути помилку вже після успішного commit вибору.
5. **Конкурентна зміна.** Repair порівнює snapshot у транзакції. Фоновий постер Confirm читає поточний запис і далі окремо викликає SaveMoviesBatch. Між ними можливе ручне виправлення; автоматичний позитивний upsert також потребує перевірки пріоритету новішого ручного вибору. Захист від unresolved сам по собі ці два випадки не покриває.

До доказу еквівалентності або рішення власника зберегти потрібну редакторську підказку та її invalidation. Врахувати повернення до старого EXE: старий рядок L2 після нового ручного вибору має бути інвалідований навіть у перехідній версії.

**Механізми з іншою семантикою.**

- `claimSearchAttempt`: map в контексті одного послідовного pipeline, ключ query/обидва роки/type/мовна стратегія. Зберігає факт спроби до завершення виклику. Після вилучення SearchCacheKey задати ці поля безпосередньо в attemptIdentity. Зберегти область одного файла, у плані розрізняти exact та ranked. [Спроби](../../internal/tmdb/search_attempts.go#L16)
- `detailsGroup.DoChan` за type:id та `modelsGroup.Do` за каталогом об'єднують одночасну роботу до її завершення. Без них збільшуються одночасні запити. Запит details використовує ctx першого caller, waiter окремо може вийти через свій ctx. Перевірити скасування лідера і незалежного waiter. Для search спочатку виміряти накладення; якщо потрібне об'єднання, використати наявну бібліотеку singleflight лише для однакової **сирої HTTP-відповіді** за endpoint/query/queryYear/мовою та рештою параметрів одного клієнта. Окремий простір ключів від details/catalog, незалежне оцінювання targetYear і контексту. Не розділяти між воркерами змінювані slices. Таймінг запитів без цього механізму не впливає на холодне послідовне розпізнавання.
- `movies` за filename зберігає підтверджений вибір користувача між запусками. Локальний постер зберігається як файл за очищеним ім'ям (caller додає ID), DownloadPoster пропускає наявний, успішний обхід дозволяє orphan cleanup. Видалення каталогу втрачає ручні виправлення, видалення постерів погіршує офлайн-вітрину. Для позитивного L1 перевіряти окремі шляхи постерів навіть для тієї самої identity. [Постери](../../internal/tmdb/client.go#L846)
- `localization_fingerprint` у movies фіксує завершений snapshot (тип, ID, UA/EN, plot), умовний UPDATE після успіху. Зміна snapshot повертає eligibility. Без маркера повторний scan може знову витратити переклад на той самий придатний оригінал. Кеші введених hint/type у JS зберігають чернетку редактора за filename. Жоден з цих механізмів не має права вибирати identity. [Snapshot](../../internal/storage/localization.go#L12) · [Стан редактора](../../frontend/src/editor-state.js)

**Ціна вилучення Search L1.** Перевіряти серії файлів із однаковою назвою, різні папки та повтори всередині AI verification. Search і частина alias URL можуть повторитися між файлами; наявний details cache обмежує повтори details. На наступному scan L1 і сьогодні очищається. Нові/unresolved шукаються знову, для вже підтверджених файлів очікуємо нуль саме recognition calls; окремо рахувати backfill, discovery й переклад. Exact, IMDb, компактний список і прямі details мають власні входи; AI-assisted уточнення може виконувати ranked fallback і відчує вилучення. Холодний miss без придатного наступного кандидата залишиться miss.

| Власник | Контракт після спрощення |

| Координатор у `main` | Приватна функція/структура у тематичному файлі, отримує file inputs і наявні клієнти. Визначає черговість спроб, pending і бюджет. Повертає перевірені результати чи причини завершення по файлах. Не володіє БД, HTTP transport, Wails або фоновими воркерами. Пакет main уже імпортує всі потрібні типи. |
| `internal/tmdb` | ParseFilename, варіанти та typed search, ranking, перевірка identity за details, локалізований водоспад uk-UA → ru-RU → en-US з раннім виходом. Одна реалізація отримання search rows; окремі функції exact, shortlist, ranked, direct ID. |
| `internal/ai` | Контекст запиту, виклик конкретної дозволеної моделі через наявний транспорт, кореляція, валідація Groq confidence 0–1, provider/model, квота й лімітери. Окремий TranslateBulk. Для початкового перенесення залишити RecognizeBulk. |
| `internal/storage` | Batch і guarded update, SQL захищає перехід стану. Адаптер запису в App формує Movie, викликає commit і передає лише реально збережені filename на локалізацію. |

**Один файл.** App передає стабільний filename, диск-шлях, корінь, parsed input і уточнення grouped TV. Координатор спочатку перевіряє IMDb (окремий lookup), потім запускає deterministic TMDB, далі лише для pending отримує AI-гіпотези. Локальний rescue для порожньої назви виконується в чинному місці та межах кореня. Для гіпотези AI виконується exact, а non-strict може перейти на чинний ranked fallback; суворий тип обмежує endpoint. У разі прийняття повертаються details, джерело, confidence і review. Після вичерпання допустимих спроб App готує placeholder тільки для файла без підтвердження. Переклад виконується після commit.

**Представлення.** Розширити наявний searchAttempt тільки потрібним походженням: source, query, queryYear, targetYear, mediaType; режим і перелік мов задає виклик. Пріоритет задає позиція у slice. Порядок будується з чинних buildAttempts/pipelineLatin/pipelineCyrillic і перевіряється snapshot послідовності, включно з очищенням, parent та транслітерацією. Для AI брати rec.Year і зберігати filename year як окремий доказ. Для IMDb передавати IMDb ID як ID, для ручного exact будувати одну введену гіпотезу, для редактора викликати власний упорядкований генератор. Орфографічні варіанти на кшталт наявного Sk→Sc належать лише дозволеному rescue. Новий ё/е потребує окремого рішення. Позначка «вже перевірено» живе в локальному seen для того самого файла, режиму і контексту перевірки. Не сортувати за ітерацією map. До формування AI batch відновлювати початковий стабільний порядок шляхів за ordinal, бо канал воркерів його не гарантує.

**Мінімальний результат однієї перевірки**: `(*tmdb.MovieInfo, error)`. Позитивна узгоджена пара ID/тип → (info, nil), повний придатний пошук без прийнятного збігу → (nil, nil), збій API/декодування/невідповідні details → (nil, err), STOP/deadline → (nil, ctx.Err()). За часткового збою пам'ятати першу помилку в межах дозволеного каскаду. Якщо чинні правила дозволяють прийняти пізніший підтверджений результат, повернути його. Якщо прийняття немає й залишився невиконаний потрібний запит, повернути помилку. Скасування має пріоритет до наступного кроку, помилка TMDB не витрачає semantic AI retry. Для batch достатньо результатів за ключами вхідних файлів та помилки операції. Placeholder з причиною unresolved і повідомлення про outage можуть співіснувати за успішного commit; скасовану транзакцію не рахувати.

**Bounded subset retry, окремий дослід.** Зафіксувати snapshot моделей і ключі вхідної пачки. Після кожної моделі корелювати request_id, legacy ID приймати лише однозначним, перевірити resolved/status, EN, confidence та TMDB. Прийняті файли вилучати з pending назавжди для цієї операції. Залишок зберігає свої ID і порядок: у пачці 8+2 друга модель бачить саме двох. Невідомі ID відкинути, дубль з конфліктом повернути до pending лише для відповідного файла. Не повторювати вже перевірену рівнозначну гіпотезу в тому самому режимі. Пропозиція бюджету для тесту: один додатковий semantic крок на pending batch, кожну модель з snapshot не більше разу на цей крок/каскад без перезапуску курсора, transport retries рахувати окремо. Заборонити наступний крок після cancel, порожньої pending або недоступного TMDB. Чинну послідовність Gemini, потім Groq за наявності, інакше legacy xAI, та обробку quota lock зберегти. Чи дозволяти semantic retry до резерву і з яким бюджетом, вирішує власник. Для перевірки впливу лише кешів обидва варіанти спочатку працюють зі старою retry-політикою.

## 8. Рекомендоване рішення

Обрати B через конкретний перехід «успішно декодований AI batch → верифікація кожного файла → наступна модель». Лише після TMDB стає відомо, кого можна вилучити з pending. У A цю інформацію довелося б передавати назад усередину AI-клієнта або повторно запускати каскад з App. Найменший крок до B: перенести наявну координацію в приватний компонент пакета main, дати App один результат на файл і лишити єдиний production-вхід. У C немає виявленого завдання, яке вимагало б переписати scanner, Repair, схему або Bridge. Новий `internal/recognition` мав би сенс за появи незалежного другого споживача чи реального циклу залежностей. Зараз його введення додало б експорт типів і адаптацію без цього виграшу.

## 9. Контрольні сценарії

**Постановка експерименту.** Позначення A у вимірах означає **незмінний checkout** із §2, а не виконаний мінімальний рефакторинг із §7. B запускається лише після окремого погодження у тестовій ревізії. На однакових іменованих fixtures спочатку порівняти A з перенесенням без зміни політики, далі окремо без L1, без автоматичного L2 та з обома змінами. Alias key, виправлення error semantics і semantic retry оцінювати окремими дельтами. Так зменшення unresolved після другої моделі не буде приписане вилученню L1.

Для кожного fixture зафіксувати вхідні шляхи/корені, initial rows movies/L2, snapshot моделей, правильні пари (filename, тип, ID) або очікуваний unresolved та допустимий review. Одна копія тимчасової SQLite на запуск, один і той самий scripted AI, `httptest` чи fake RoundTripper для всіх endpoint включно з аліасами, details і постером. Відповіді прив'язувати до параметрів і номера спроби конкретного URL; невідомий запит завершує тест. Для AI фіксувати модель та список request_id. Бар'єрами на каналах керувати порядком worker completion, commit, manual edit та cancel без sleep. Окремі прогони: холодний клієнт, прогрітий клієнт, зворотний порядок файлів, повторний scan тієї самої БД, перезапуск з тією самою БД. Порівнювати з незалежним еталоном і між варіантами: історична помилка A не є еталонним результатом.

## 10. Implementation Plan

Кожен рядок є окремою майбутньою зміною. Після кожного програма має один робочий production-шлях. Rollback означає повернення відповідної зміни в коді після тесту без зміни схеми чи відновлення БД.

| Етап / залежність | Файли, функції, що змінити або прибрати | Що зберегти, перевірка та умова прийняття | Коли відкотити |
| --- | --- | --- | --- |
| 0. Baseline, незалежний | Лише майбутні fixtures у root, tmdb, ai, storage tests; відтворити A і таблицю вище. | Усі режими й дані без змін, кожен результат прив'язаний до еталона та бюджету запитів. | Нестабільна fixture: виправити стенд до зміни production. |

## 11. Ризики та відкриті питання

- **Факти checkout.** Ранній L1 hit, нетипізований ключ aliases, два різні AI-verification, два способи кореляції та L2 до commit спостерігаються в коді. Прямі guards для typed details уже існують у ranked search і Repair. Давні пропозиції з аудиту потрібно перевіряти по кожній точці входу.
- **Архітектурний висновок.** Поточні бізнес-режими потрібні. Менше прихованого стану дають винесення рішення про pending та усунення міжфайлових рішень. Автоматичне вилучення L2 змінює положення чинного AGENTS.md щодо versioned replay; production-перехід потребує погодження цього контракту.
- **Гіпотези.** Частота L2 recovery після rollback, економія alias/details, зміна тривалості та користь наступної моделі не виміряні. Поліпшення прикладу Guarding Stars за рахунок L1 не доведено. Повторні fake-запити показують структуру витрат, але не реальний відсоток влучань у бібліотеці.
- **Рішення власника.** Допустимі витрати за класом fixture, семантичний бюджет/перехід до reserve, доля унікальної historical AI-назви й потреба зберігати історичну модель після відмови від L2. До рішення зберегти наявні provenance та інвалідацію там, де вони ще потрібні. Окремо вирішувати нові spelling і правила exact. Пороги acceptance року, схожості й Groq не змінювати разом із реорганізацією.

## 12. Acceptance Criteria

**Протокол вимірів.** Одна строка на fixture/варіант/повтор. Для кожного filename порівнювати правильні підтвердження, хибні підтвердження та unresolved із незалежним oracle; зберігати самі розбіжні пари, щоб середнє не приховувало регресію. Рахувати реальні TMDB wire calls за endpoint, мовою та retry, AI inference за моделлю й складом batch, повтори одного URL і повтори тієї самої гіпотези. Окремо discovery, переклад і poster. Виміряти wall time серії на одному стенді, подати медіану та розкид; для fake wait окремо записати контрольоване очікування. SQLite: спроби, committed batches/rows, rollback та L2 statements, перевіряти кінцевим SELECT. Cancellation: точка сигналу, останній фактичний запит, результат і час виходу, last_scan_at, збережені commits. Детермінованість: повтори та перестановки воркерів дають ті самі identity, ordered shortlist, причини review й склад AI batch. Manual corrections: порівняння filename/тип/ID/назв/опису після конкурентного фону. Архітектура: порахувати власників рішення «далі до AI», реальні реалізації кореляції/typed URL, карти з рішеннями між файлами, нові пакети/типи та обов'язкові залежності для одного fixture.

| Рішення | Необхідні докази |
| --- | --- |
| **ACCEPT** | Нуль нових хибних identity і втрат раніше правильних без погодженої зміни oracle. Паритет manual/Repair/Wails API, DOM і payload подій. Транзакції, filename, захист review/UA, WAL, synchronous=NORMAL, busy_timeout=5000, foreign_keys=ON та один connection збережені. STOP, shutdown, guards фонових записів і deterministic tests проходять. Один власник автоматичного pending, одна кореляція, нуль міжфайлових кешованих search-рішень, немає нового прихованого стану. Для кожного додаткового запиту є джерело і скінченна межа, заздалегідь погоджені бюджети виконано, лімітери збережені. |
| **PARTIAL** | Незалежний етап задовольнив свої критерії, наприклад L1 прибрано, але редактор досі потребує L2 або subset retry перевищує бюджет. Приймати можна лише виміряний незалежний етап. |
| **REJECT** | Хоч одна нова хибна identity, втрачена ручна корекція/можливість, пошкоджений commit, запит після STOP на визначеному бар'єрі, непередбачуваний вибір, безмежні повтори, порушення ліміту чи нового hard budget. Повернути останню прийняту ревізію. |
| **UNRESOLVED** | Немає oracle/fixture, підтвердженого бюджету, зіставних вимірів чи реалізованого B. Позитивний unit-тест A і скорочення рядків коду не закривають ці прогалини. |

**Поточний статус B: UNRESOLVED.** Створено проєкт експерименту й перевірено частину baseline A. Результати B, включно з кількістю запитів, швидкістю та часткою правильних identity, ще не отримано.

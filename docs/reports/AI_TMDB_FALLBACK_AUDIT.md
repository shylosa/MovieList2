## 2. Фактичний Recognition Pipeline

`RunScan` фіксує порядок моделей у контексті, реєструє cancel, очищає TMDB-кеші й скидає Gemini quota lock. `StopScan` скасовує контекст операції. `shutdown` скасовує scan і Repair, чекає фонові операції і тоді закриває клієнт TMDB та БД. Паралельний прогрів каталогу Gemini має lifecycle-контекст, як і `finalizeScan`, тому може пережити STOP. Прогрів окремо від recognition може звернутися до каталогу моделей. Після обходу запускається можливе дозаповнення рейтингу за збереженим ID, також окремо від пошуку identity. [RunScan](../../app.go#L727) · [Каталог моделей](../../app.go#L639) · [Рейтинг](../../app.go#L914) · [StopScan](../../app.go#L963) · [Shutdown](../../app.go#L182)

У таблиці запит означає логічний виклик endpoint або inference. Повтори HTTP, мови, аліаси й формули витрат наведено в розділі 4. Перевірка контексту відбувається перед викликами й у циклах, а запис використовує ctx транзакції.

## 3. AI Cascade

### Межа, на якій нині завершується перебір

Поточні сигнатури `RecognizeBulk(ctx, []FileRecognitionContext) ([]RecognizedTitle, error)`, `retryMissingRecognitions(ctx, []FileRecognitionContext, []RecognizedTitle) ([]RecognizedTitle, error)`, `requestWithRetry(ctx, prompt string)` та `makeRequest(ctx, prompt, modelName string)` розділяють пакет, кореляцію, перебір і один запит. `makeRequest` перевіряє наявність відповіді SDK та парсить JSON. `requestWithRetry` на `err == nil` маркує кожен рядок `Provider="gemini"`, `Model=modelName` і повертає весь результат. Аргументом перебору є prompt. Він не має доступу до TMDB-рішення для файла. [RecognizeBulk](../../internal/ai/gemini.go#L270) · [Кореляція](../../internal/ai/gemini.go#L295) · [Перебір](../../internal/ai/gemini.go#L351) · [Запит](../../internal/ai/gemini.go#L427)

| Стан | Фактична реакція |
| --- | --- |
| HTTP/API/SDK error, відсутні кандидати/parts, JSON не декодується у потрібний тип | `makeRequest` повертає помилку, перебір іде далі при активному ctx. 404/`not_found`/`no longer available` позначає модель недоступною до refresh. Якщо Gemini вичерпані, викликається резервний провайдер. |
| JSON декодується, проте структурно бракує полів | Gemini просить required schema, але локальний parser лише робить `json.Unmarshal`. Відсутній `confidence` стає `0`, порожні/невідомі поля не запускають перебір. `[]` або `null`, якщо отримані як придатний для парсингу текст, дають відсутні елементи й переходять до `retryMissingRecognitions`. Groq додатково перевіряє явне числове confidence для всіх повернених рядків. |
| Повернуто частину `request_id` | `RecognizeBulk` призначає `recognition-N`, якщо ID не задано. `retryMissingRecognitions` бере за `request_id`, або за legacy `id` тільки для рядків без `request_id`. Відновлює порядок входу, по одному повтору каскаду для кожного пропуску. Курсор попередньої моделі не переноситься. Відомо недоступні моделі пропускаються, quota lock може скерувати повтор одразу в reserve. |
| Валідний ID, порожня назва / confidence 0, нижче 0,55 або status `ambiguous` / `unresolved` | Це зіставлений рядок. Нового AI-запиту немає. Порожня назва запускає лише папковий rescue. Слабкий рядок з непорожньою EN-назвою відхиляється у merge до TMDB. `OriginalTitle`, `PossibleYears`, `Country`, `DirectorOrCreator` і `Reason` не підставляються як самостійні гіпотези. |
| `media_type` порожній або сторонній, решта придатна | Модель не змінюється. Merge вважає preferred type `movie`, допускає обидва exact endpoints у non-strict і застосовує умову типу/JW. У L2 пишеться сирий тип AI. |
| Гіпотеза TMDB не знайдена або відхилена | Merge повертає порожню identity. Черга зберігає unresolved за можливості і не відновлює AI-каскад. Різні причини фіксуються різними логами, але на межі `storage.Movie` всі промахи, відхилення й частина помилок мають однаковий `TmdbID=0`. |

### Резерв, quota та cancellation

- `grokRecognizeFallback(ctx, prompt)` обирає `groqRecognizeFallback(ctx, prompt)` за наявності Groq-ключа. Інакше йде в xAI, якщо його налаштовано. Після вичерпання Groq xAI не додається. Legacy xAI має той самий JSON parser, що й Gemini. Groq вимагає confidence `[0,1]`, один пропущений/null/out-of-range confidence відхиляє всю відповідь. Валідний confidence `0` припустимий для transport/parser і семантично завершує поточний перебір так само. Поріг merge 0,55 спільний, верхня межа після Gemini/xAI локально не перевіряється. ### Ранжування, кеш і ціна

- Автоматичний `scoreResult` бере точну назву 200, contains 70 або 35, JW понад 0,95 / 0,90 / 0,85 дає 150 / 120 / 80. Оригінал + точний рік додає 300, рік додає 150 / 80 або штрафує −400 від двох років, збіг типу додає 30. При title score <100 можливі аліаси для перших 3 рядків кожної відповіді. Нульовий title score відхиляється. Спочатку враховується `identityScore`, у вікні 30 балів діють фінальні бали з мовою та популярністю (бонус до 50). `rankResults` вимагає 170 без року, 150 при точному, 190 при сусідньому, 220 при конфлікті. Код відсікає корінь, generic або порожню назву, конкретну підумову журнал не ідентифікує. Рядки scan підтверджують один inference і нуль резервних викликів. Журнал не містить знімка списку моделей тієї операції, тому наявність та працездатність наступної моделі невідомі. Та сама умова завершення застосовується до всіх файлів цього шляху. [AI stop condition](../../internal/ai/gemini.go#L379) · [Порожня назва](../../app.go#L1367) · [Папка](../../app.go#L1720)

**Недостатні докази.** В автоматичному trace немає `candidate_ranking_summary`, `search_success` чи `year_mismatch_blocking`; немає й DEBUG-подій із кандидатами та поясненнями їх відхилення. Тому конкретні ID, raw results і score автоматичних відповідей невідомі. Нуль лічильника cache hit не охоплює L1; очищення кешів і відсутність `tmdb_l1_cache_hit` / `ai_cache_hit` для цього файла не свідчать про фактичне блокування кешем. `original_title`, `status`, `possible_years`, `reason` та raw payload у відповідному фрагменті не зафіксовані. Доступні рік і тип самі по собі не дають ідентичності. [Рівні логування TMDB](../../internal/tmdb/search.go#L645) · [Поля AI log](../../app.go#L1354) · [API counters](../../internal/tmdb/client.go#L798)

**Гіпотези.** Відмінність `ё/е` могла вплинути на пошук або scoring. Запиту `Охрана звезд` у trace немає, його результат у TMDB невідомий. Інша модель могла б запропонувати `Guarding Stars`, але її відповідь і результат автоматичної верифікації не спостерігалися. Ручний результат підтверджує доступність кандидата за введеною англійською назвою в конкретній ручній операції. Мінімальна зміна для цього класу відмов дає зіставленому empty/low-confidence елементу один обмежений шанс у наступній моделі після локального rescue. Знахідка з L1 стосується ширшого класу випадків, для Guarding Stars її вплив не встановлено.

## 7. Варіанти виправлення

Пачка 10, усі `request_id` повернуто. Вісім правильних гіпотез проходять TMDB. Дев’ятий має правдоподібну неправильну назву, яку TMDB не підтверджує за поточними правилами. Десятий має `en_title=""`, confidence 0. Сьогодні `RecognizeBulk` повертає 10 зіставлених рядків після одного успішного inference. Десятий іде в папковий rescue, дев’ятий у TMDB merge і після відхилення дає unresolved. За промаху rescue та успішного SQLite commit виходить 8 підтверджених і 2 unresolved без другого inference. Якщо хибна назва сама приведе до іншого TMDB-твору, який проходить усі наявні перевірки, система може його прийняти. Факт TMDB-підтвердження гіпотези гарантує конкретний TMDB-запис, а відповідність локальному файлу залежить від доказів назви, року, типу й контексту. ## 8. Рекомендована архітектура

Рекомендовано підхід 2 за варіантом E. Він охоплює обидва промахи з прикладу і використовує TMDB-рішення до повторного inference. Підхід 1 можна застосувати як коротке виправлення P1.1, якщо власник обмежить зміни до порожніх, слабких і відсутніх відповідей. Курсор у варіанті E запобігає повторному старту з першої моделі після кожного невдалого елемента.

1. Ініціалізувати pending у стабільному порядку входу. Згенерувати унікальні `request_id` один раз для цієї пачки й зіставити з локальними файлом та slot. Невідомий `request_id` відкинути. Дублі обробляти детерміновано за правилом, яке виключає присвоєння гіпотези іншому файлу. Однозначний legacy `id` дозволити тоді, коли response ID відсутній.
2. Використати наявний детермінований пошук scan перед AI. Кожен крок AI приймає pending subset, повертає transport error або корельовані per-item outcomes. Явно розрізняти missing, invalid fields, empty/low/unresolved, придатну гіпотезу, остаточне TMDB-відхилення, недоступність TMDB, cancellation і прийнятий результат. Поточний автоматичний папковий rescue виконувати щонайбільше раз на файл, зі спільним дедупом спроб за потреби. Статуси й provenance логувати без prompt, raw payload і шляхів до медіатеки.
3. Придатні гіпотези верифікувати тим самим обмеженим TMDB-шляхом. У межах пачки пам’ятати вже перевірену форму `title + year + preferredType + strictness` для конкретного файла, щоб ідентична відхилена гіпотеза не повторила exact search. Це стан поточної операції поверх наявних кешів. При зміні року, типу чи режиму верифікація може дати інший результат. При недоступності TMDB зупиняти шлях, який потребує цієї недоступної перевірки, або повторювати саму перевірку за бюджетом transport, зберігаючи інші підсумки.
4. Після прийняття видалити файл із pending. Рухатися до наступної дозволеної моделі або налаштованого резерву за наявності бюджету. Як стартовий ліміт для погодження запропоновано один додатковий **семантичний** раунд на batch після першої декодованої пачки. Дозволені model steps проходять один раз у тій самій послідовності; transport failures можуть вимагати кількох кроків до декодованої відповіді. Для `G` доступних Gemini моделей і `R` моделей вибраного резерву цей шлях має максимум `G+R` логічних inference на первинну пачку в одній операції, включно з транспортними невдачами. У поточному клієнті максимальна оцінка за умови синтаксичної відповіді з `m` пропусками становить `(1+m) × (G+R)` кроків, зі спільним quota lock та unavailable registry. Фактична кількість wire-запитів SDK може відрізнятися від лічильника `GenerateContent`.
5. Атомарно записувати підсумок batch для прийнятих і звичайних unresolved, зберігаючи SQL-гарантії і чинний `movies.filename`. Врахувати, що довший пошук дає більше часу для паралельного ручного підтвердження. Тест на таку гонку має гарантувати збереження підтвердженої вручну identity. Для цього можна застосувати чинну транзакційну схему перевірки актуального запису, яку використовує `SaveRepairedMovie`. На cancellation поважати rollback активної пачки й результати попередніх commit. Після успішного запису публікувати acceptance, зберігати L2 з походженням гіпотези і ставити на локалізацію лише підтверджену identity. `TmdbID>0`, валідні українські поля, нормальний unresolved і послідовність fallback є незмінними умовами прийняття. [SQL upsert](../../internal/storage/storage.go#L64) · [Транзакційний guard](../../internal/storage/storage.go#L405) · [Localization](../../app_localization.go#L19)

У прикладі 8+2, якщо наступна модель доступна й її транспорт вдається, E додає один inference на два ID. У двох нових гіпотезах буде до 4 exact typed search URL, до 12 alias URL, до 6 details URL і до двох постерів **на exact-етапі**, до retries та кешів. Чисті exact-промахи відкривають до 2 каскадів `FetchByCleanTitle` на гіпотезу за умовами розділу 2. Відсутня, слабка або повністю дубльована гіпотеза дає 0 нових запитів верифікації. Gemini limiter може додати до приблизно одного інтервалу 4 с очікування в ізольованому потоці з одним додатковим запитом, reserve має інтервал 2 с. За спільного навантаження та мережевих повторів затримка змінюється; вимір потрібен на локальних сценаріях із контрольованим часом. [AI limiter](../../internal/ai/gemini.go#L145) · [Exact search](../../internal/tmdb/search.go#L185) · [AI verify](../../app.go#L1511)

**Виправлення контракту.** Однозначна кореляція, typed alias cache, область L1 на одну спробу, відокремлення HTTP-помилки від справжнього miss, guard пари ID/тип, узгодження L2 та метрики після commit. Підтримка окремого стану невдалого елемента дозволяє виправити дефект передчасної зупинки без послаблення порогів.

**Рішення власника.** Затвердити семантичний бюджет і можливість переходу до резерву після усіх придатних за транспортом, але дійсно невдалих гіпотез. Зберігати поточне `Gemini → Groq, або legacy xAI за відсутності Groq` та чинну поведінку 429 до окремого рішення про розрізнення provider quota і model rate limit. Розглядати інші поля AI, `ё/е`, NFC і зміну режимів редактора як окремі зміни правил пошуку. Для `ё→е` можливий окремий пізній пошуковий варіант після наявних детермінованих спроб і перед AI, лише для кириличного базового заголовка з `ё/Ё`. За погодження почати з одного preferred typed URL `ru-RU`, зі збереженим `targetYear` і чинною перевіркою; відсутність року або результатів може стати підставою для окремого експерименту на додатковій мові/типі. Власний ключ має відповідати реальному query/рокам/типу/мовній стратегії, без folding разом із запитом `ё`. Початковий бюджет такого експерименту становить до 1 додаткового search URL на придатний файл, до 3 спроб цього URL, плюс можливі аліаси, деталі й постер. Користь для Guarding Stars невідома.

## 10. Implementation Checklist

1. **Підтвердити локальні дефекти тестами.** Зафіксувати mixed batch 8+2, duplicate/mismatched IDs, negative L1 із різними папками, alias collision `movie:N`/`tv:N`, mismatch у details. Для Guarding Stars використати фіктивні відповіді як доказ клієнтського маршруту, із позитивним і негативним сценарієм lookup за `е`.
2. **Виправити кореляцію і typed identity окремим кроком.** Довірений локальний slot і legacy guard у `internal/ai`/`processGeminiQueue`; typed alias cache; спільна перевірка ID/типу для exact і `/find`. Прогнати тести ручного IMDb, exact, candidates та strict type.
3. **Виправити область L1 і класифікацію TMDB-помилок.** Лишити per-attempt cache, продовжувати каскад після base miss, зберігати negative лише для достатніх успішних відповідей і прибрати file-specific poster path із title cache. Зафіксувати cache hits та фактичні typed requests до/після.
4. **Додати семантичний pending retry в автоматичний scan.** Після погодження бюджету реалізувати cursor, per-item outcomes і bounded verification. Застосувати чинні пороги, snapshot моделей, rate limiting, правила резерву й cancellation. Прогнати mixed batch, quota, malformed Groq row, transport/TMDB outage та перевірити payload підмножини.
5. **Погодити результат із записом.** Спільні guards для L2, збереження provider/model, acceptance після commit і чинний `SaveMoviesBatch`. Перевірити rollback, unresolved, стабільність filename, підтверджені українські поля та локалізацію після успішного запису. Рішення про зміну `recognitionPipelineVersion` приймати за результатом replay-тестів на сумісність старих рядків.
6. **Окремо погодити обмежений експеримент `ё/е`.** Спочатку scoring на вже отриманих результатах із негативними контролями. Другий незалежний крок за рішенням власника додає один late typed запит, з тестом ключів, бюджету, неоднозначностей і відсутності змін у редакторі. Оцінити результати на репрезентативних офлайн fixtures. Для live перевірки потрібен окремий дозвіл.

Кодові виправлення P1.1–P1.3 і P2.1–P2.2 обґрунтовані поведінкою поточного каскаду. До наступного запиту на реалізацію можна включити кроки 1–5 із бюджетом одного додаткового семантичного раунду. Розширення пошукових правил із кроку 6 залишається окремим рішенням.
